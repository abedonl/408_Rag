# 面试表达篇：408-RAG + Agent 备考助手

> 用途：面试现场「怎么说」，不是功能说明书。技术细节以 `docs/interview-prep.md` 为准，本文只负责把已有事实讲成面试官能听懂、能追问、且你不会被问穿的话。
>
> 数字口径：截至 2026-11-05。本地全量测试 **223 passed**，CI 只跑 adversarial 单测 **10 passed**；README 里的「135 passed」是旧数字，被追问时主动承认并说明。
>
> 标记说明：`【待补】` 表示项目里没有可信数据，现场必须说「没测过/待补」，不能估。

---

## 0. 面试前 60 秒速查

**最能打的三句**

1. 「这不是一个聊天机器人，是一条可评测的检索 + 有界 Agent 链路：每个结论都有数字，负结果也留在报告里。」
2. 「Agent 只有 3 轮、7 种终态、9 个带契约和超时的工具；它的边界是写死的，不靠模型自觉。」
3. 「19 轮多轮评测：通过率 94.7%，澄清召回 100%，指代消解 100%，总成本 0.17 元；但样本小，我不拿它证明泛化。」

**最容易翻车的三处**

1. 说「Agent 显著优于 RAG」——21 题置信区间下界是 0，只能说方向一致。
2. 说「引用 100% 准确」——真实口径是「可溯源率 100%（97/97），本考点引用率 95.9%」。
3. 说「成本就是账单」——当前模型不在单价表，成本是按默认单价估算的下界。

## 1. 电梯陈述

### 1.1 30 秒版本（逐字可背）

> 我做了一个面向 408 考研的真题 RAG 与 Agent 备考助手：底层是 720 道 2009–2026 真题、5296 个教材 chunk、6182 个知识点节点，走 dense + sparse + BM25 三路检索再做融合；上层是一个有界 plan-act-observe Agent，最多 3 轮工具调用，必须落到 7 种 stop_reason 之一，工具全部用 Pydantic 契约加独立超时。
>
> 我重点做的不是堆功能，而是把每个取舍都做成可复现的评测：检索有消融，Agent 有三路对照，多轮有 19 轮用例，负结果也留在文档里。比如交叉编码器重排经消融是负收益，我就没上。

**口播提示**

- 「有界」「7 种终态」「负结果」三个词要重读，这是和普通 RAG Demo 的分界线。
- 不要一口气报完所有数字，30 秒只留 720 / 3 轮 / 7 种 / 三路检索。

### 1.2 2 分钟版本（按四段讲）

**第一段：问题（约 20 秒）**

> 408 备考的真实痛点不是找不到资料，而是三件事：不知道什么值得背、不懂的知识点查不动、计算题和图表题看不懂。通用大模型能聊，但它给不出真题频次，也经常编真题编号。

**第二段：方案（约 50 秒）**

> 我用两层解决。第一层是检索：真题和教材切块后进 Qdrant，dense、BGE-M3 sparse、BM25 三路召回，按题型路由选路，zscore 融合后做小节去重，再把父节上下文交给生成。第二层是 Agent：LangGraph 的 StateGraph，显式节点和条件边，但决策不交给自由 ReAct；规则先路由，工具只能从 9 个白名单里选，每个工具有 Pydantic 参数契约、独立超时和错误类型；会话记忆是内存 LRU，200 个会话、2 小时 TTL，超过 8 轮压成规则摘要；指代消解用规则，解不出来就反问，不硬猜。
>
> 另外有一条对抗规划链路：先出 Plan，再用规则 Critic 质疑，最多修订一次，避免「假大空」的学习计划。

**第三段：证据（约 35 秒）**

> 检索在 dev 452 题上 Accuracy@10 是 0.668，held-out 99 题是 0.687，P50 约 50ms 级；Agent 在 21 题配对集上是 95.2%，单轮 RAG 85.7%，纯 LLM 90.5%，但置信区间还跨 0，所以我只说方向一致；多轮 19 轮通过率 94.7%，澄清召回和指代消解都是 100%，总成本 0.1744 元；60 题 held-out 端到端 78.3%，排除 8 个空回答后可判题 90.4%。

**第四段：边界（约 15 秒）**

> 我知道短板在哪：没有 holdout 上的三路 baseline，规则指代有天花板，记忆重启即失，单机串行没有并发和 P95 数据。这些我都写进文档，下一步优先补 baseline 和压测。

**口播提示**

- 第三段不要念表格，只念「0.668 / 95.2 / 94.7 / 78.3」四个锚点。
- 第四段必须主动说，面试官往往就在等你这句话；说完停顿，让他接。

### 1.3 差异化三点（被问「你和别人有什么不同」时用）

| 差异点 | 一句话表达 | 证据 |
|---|---|---|
| 有界 Agent，不是自由循环 | 「轮次、预算、终态、工具白名单全是硬约束，模型没有无限发挥的空间。」 | 3 轮上限、90 秒预算、7 种 stop_reason、9 工具契约 |
| 评测驱动取舍 | 「每个模块都有独立评测，连输的那一路也留着。」 | 检索消融、Agent 三路、19 轮多轮、对抗 40/40 |
| 可解释与可运维 | 「每轮能看到 stop_reason、工具调用、token 和人民币成本，出问题能定位到节点。」 | trace、成本追踪、推理链展开 |

## 2. 三段讲述结构：问题—方案—证据

> 适用于「介绍一下你这个项目」这种开放题。总时长控制在 3 分钟，每段之间留半秒停顿。

### 2.1 问题段（40 秒）

**该说什么**

- 用户是谁：408 考研学生，不是泛知识问答用户。
- 三个具体痛点：背什么、查不懂的、计算/图表题。
- 通用大模型的两个硬伤：给不出真题频次；会编真题编号和年份。
- 一句转折：「所以我要的不是更会聊，而是更可核对。」

**避免说什么**

- 不要说「RAG 可以解决大模型幻觉」这种大而空的结论，面试官会追着问「怎么证明」。
- 不要展开考研市场、用户规模，没有数据支撑。
- 不要贬低通用模型，重点讲「场景需要结构化证据」。

**可用逐字稿**

> 408 的痛点很具体：学生不是没资料，是不知道哪些真题反复考、教材哪一节对应哪道题、计算题和图表题光看文字看不懂。通用模型能解释概念，但它给不出「死锁考过几次、分别是哪几年」这种统计，还可能把 2021 记成 2019。所以这个项目的第一目标不是生成更流畅，而是让每个结论都能回到真题或教材。

### 2.2 方案段（80 秒）

**该说什么**

- 先讲两层结构：检索层、Agent 层，再讲一条对抗规划链路。
- 检索层只讲四个动作：切块与父子结构 → 三路召回 → 按题型路由 → zscore 融合 + 小节去重。
- Agent 层只讲四个约束：显式图、3 轮、7 终态、工具契约与超时。
- 多轮能力单独一句：内存 LRU + 规则指代 + 澄清短路。
- 最后一句取舍：「重排我试过，消融是负收益，所以关掉。」

**避免说什么**

- 不要从「我用了 LangChain」开始讲技术栈，先讲问题和结构。
- 不要罗列 9 个工具的名字，挑 3 个有代表性的：检索、计算器、真题统计。
- 不要把「有记忆」说成「长期记忆」，它是内存态、重启即失，后面要主动承认。

**可用逐字稿**

> 方案分两层。检索层把真题、教材切块后进 Qdrant，dense、sparse、BM25 三路召回，按题型选路，融合后按小节去重，再把父节上下文给生成，避免只拿到碎片。Agent 层用 LangGraph 的 StateGraph，把路由、检索、规划、工具、观察、校验、回答做成显式节点；但决策不交给自由 ReAct：最多 3 轮工具，90 秒预算，必须落到 answered、clarification、no_evidence、tool_error、budget、max_rounds、verify_retry 七种终态之一。9 个工具全部有 Pydantic 契约和独立超时，坏参数返回 validation，不会静默吞掉。
>
> 多轮这块我做得很克制：会话记忆是内存 LRU，200 个会话、2 小时过期，超过 8 轮把最早内容压成规则摘要；指代消解用规则匹配，匹配不到就返回空，让流程走澄清，不猜。

### 2.3 证据段（45 秒）

**该说什么**

- 先给检索的「有没有拿到正确小节」：dev Accuracy@10 0.668，holdout 0.687。
- 再给 Agent 三路对照：纯 LLM 90.5%、单轮 RAG 85.7%、Agent 95.2%，并立刻补「21 题、CI 跨 0」。
- 多轮给四个数：通过率 94.7%、澄清召回 1.0、指代消解 1.0、工具失败率 3.0%。
- 成本给「0.1744 元 / 19 轮」，再说这是估算下界。
- 收尾给边界：60 题端到端 78.3%，空回答 13.3%。

**避免说什么**

- 不要只报准确率不报样本量。
- 不要把 60 题的 78.3% 和 21 题的 95.2% 混在一起说。
- 不要说「成本很低」而不说口径，当前模型不在单价表里。
- 不要说「引用零幻觉」，说「编造真题编号 0，可溯源率 100%，本考点引用率 95.9%」。

**可用逐字稿**

> 证据分四块。检索在 452 道 dev 题上 Accuracy@10 是 0.668，99 道 2023–2026 held-out 上是 0.687，说明没有只记住训练年份。Agent 在 21 题配对集上 95.2%，单轮 RAG 85.7%，纯 LLM 90.5%；但样本小、置信区间跨 0，我只说方向一致，不说显著。多轮 19 轮通过率 94.7%，4 个澄清用例全召回，指代消解全中，工具失败率 3%，总成本 0.1744 元，约 0.92 分一轮。60 题端到端 78.3%，有 8 个空回答，排除后可判题 90.4%。

## 3. 高频追问 Q&A（20 组）

> 回答公式：先给结论 → 再给实现或数字 → 最后主动划边界。每组末尾标出哪些必须补数据。

### Q1. 为什么不用 LangChain / LangGraph？

**结论：编排用了 LangGraph 的 StateGraph，决策层没用 LangChain 的 Agent / ReAct / Chain。**

- 用 StateGraph 的原因：节点、条件边、状态合并都显式可见；`AgentState` 是扁平、可序列化的结构，方便写 `steps`、`plan_history`，也方便分层评测。
- 不用 LangChain Agent 的原因：AgentExecutor 默认让模型决定下一步，和项目要的「规则优先 + 3 轮硬上限 + 7 种终态」相反；工具契约、超时、澄清短路都需要自己控制。
- 不用框架 checkpointer / 长期记忆：项目明确不做持久化会话记忆，历史放在自己的 `InMemorySessionStore`，避免和框架生命周期绑定。

**别踩**：不要说「LangChain 不好」，说「它的默认行为不适合这个约束场景」。

**要补**：没有做「自研图 vs LangGraph」的性能对照，这是工程选择，不是实验结论。

### Q2. 为什么不用自由 ReAct？

**结论：自由 ReAct 的失败模式不可控，而备考场景要求可解释、可计费、可复现。**

- 自由 ReAct 每一轮都让模型决定「继续查还是回答」，没有硬上限时可能抖动、重复调用、成本不可预测。
- 项目改成「规则先路由，模型只在工具选择上做有限决策」：轮次最多 3 轮、总预算 90 秒、单轮工具最多 6 次、每分钟最多 60 次，超了就落 `budget` 或 `max_rounds`。
- 好处是每个终态都能在 trace 里定位：是没证据、工具错、还是轮次用完。
- 代价是灵活性：遇到需要更多探索的问题会提前收手，这时宁可返回 `no_evidence`，也不硬答。

**别踩**：不要说「ReAct 一定幻觉」，说「它的自由度与本项目的 SLA 冲突」。

**要补**：没有做「自由 ReAct vs 有界循环」的同集对照【待补】。

### Q3. 3 轮上限怎么定？

**结论：不是拍脑袋，是按工具调用链的最长必要路径定的，再用预算兜底。**

- 典型链路：路由 → 检索（1 轮）→ 发现缺统计/计算（2 轮）→ 校验或补证（3 轮）。3 轮覆盖「检索 + 一次补工具 + 一次修正」。
- 同时有 90 秒总预算，避免单轮工具慢导致总时长失控；工具本身还有 5–30 秒的独立超时。
- 超限不是报错，是显式落 `max_rounds`，前端能看到；这比无限循环后超时更容易排查。
- 多轮评测里平均轮次 0.95，说明大多数问题 1 轮内结束，3 轮是上限不是常态。

**别踩**：不要说「3 是调参调出来的」，没有调参记录。

**要补**：轮次分布只来自 19 轮小样本，真实分布【待补】。

### Q4. 怎么证明不是幻觉？

**结论：分三层证明：检索有命中、回答有引用、编号有校验；但不能说零幻觉。**

- 第一层，检索评测：dev Accuracy@10 0.668、holdout 0.687，证明「正确小节能被召回」。
- 第二层，引用评测：97 条声明里可溯源率 100%，本考点引用率 95.9%，编造真题编号 0，押题/预测表述 0。
- 第三层，流程校验：`verify` 节点检查真题编号和押题表述，失败触发一次重写（`verify_retry`）；生成失败或空正文落 `no_evidence`，不硬答。
- 边界：引用编号越界目前只记录、未纳入硬拦截；claim 评测是离线小样本，不能外推成线上零幻觉。

**别踩**：绝对不要说「我们零幻觉」。

**要补**：线上真实幻觉率、引用 precision/recall 的线上监控【待补】。

### Q5. 引用怎么保证溯源？

**结论：回答按「块」组织，每块带来源；前端可展开到真题/教材原文，校验节点再做编号检查。**

- 检索结果保留 chunk 的来源、题号、小节信息；生成时要求按来源块引用，而不是自由发挥。
- 前端每条回答下有「推理链与工具调用」可展开，能看到检索与工具返回；真题推荐卡片标出处，答案折叠。
- `verify` 检查两类硬问题：不存在的真题编号、押题/预测表述；有问题就带着 feedback 重写一次。
- 边界：`[n]` 编号越界目前只被 `check_citations` 记录，不触发重写；这是已知短板。

**别踩**：不要把「可展开」说成「逐句事实核验」。

**要补**：引用编号硬拦截后的 precision/recall 提升【待补】。

### Q6. 评测集怎么来的？

**结论：四套集子，各自回答不同问题，不混用。**

| 集子 | 规模 | 用途 | 口径 |
|---|---|---|---|
| dev | 452 题 | 检索调参与消融 | 有 ground truth |
| holdout | 99 题（2023–2026） | 检验未见年份 | 从未参与调参 |
| Agent 配对 | 21 题（概念 15 / 计算 6） | 三路同 prompt 对照 | 小样本，CI 跨 0 |
| 多轮 | 19 轮 | 记忆、指代、澄清 | 通过率 94.7% |
| 60 题端到端 | 每科 15 题 | held-out 生成侧 | 78.3%，非 reports 独立报告 |

- 多轮用例是按场景手写的：追问年份、追问学习顺序、无题号选择题、考点定位失败。
- 对抗集是「黄金 Plan 10 组 + 6 类注入 40 条」，黄金 Plan 误报 0/10，注入检出 40/40。

**别踩**：不要把 21 题、60 题、19 轮说成同一套评测。

**要补**：评测集的标注一致性、多人复核【待补】。

### Q7. 有没有 baseline？

**结论：检索有消融 baseline，Agent 有 dev 21 题三路 baseline；缺的是 holdout 上的端到端 baseline。**

- 已有：纯 LLM 90.5%、单轮 RAG 85.7%、Agent 95.2%，同一批 21 题、同一 prompt。
- 检索侧有 dense / sparse / BM25 / 融合的消融，还有 rerank 的负收益结论。
- 缺的：99 题 holdout 上没有跑纯 LLM 和单轮 RAG 的端到端对照；60 题也只有 Agent 单路数字。
- 所以现场表述必须是「dev 上方向一致」，不能说「RAG/Agent 在未见年份上净增益 X」。

**别踩**：不要把 60 题的 78.3% 和纯 LLM 的 90.5% 直接比，两者不同集、不同口径。

**要补**：holdout 三路同 prompt 对照 + bootstrap CI + 成本/P50/P95，这是第一优先补数项。

### Q8. 记忆为什么不做持久化？

**结论：当前是刻意不做，先保证边界清晰和隐私简单；不是做不了。**

- 实现是内存 LRU：最多 200 个会话、2 小时 TTL、超过 8 轮把最早轮次压成规则摘要，只保留摘要 + 最近 4 轮。
- 不落盘的原因：避免引入会话库、隐私保留策略和一致性成本；项目还没到需要跨实例共享的阶段。
- 代价：进程重启、换实例就丢历史；多副本之间不一致。
- 升级路径：Redis 按 session TTL + LRU，或接 LangGraph checkpointer；前提是先定义保留期限和脱敏策略。

**别踩**：不要把「内存记忆」说成「长期记忆」。

**要补**：记忆压缩对回答质量的影响评测【待补】。

### Q9. 规则指代消解不够用怎么办？

**结论：规则只覆盖高频模式，解不出来就澄清，这是有意为之的保守策略。**

- 规则只处理 4 类固定模式（如「那 2021 年呢」「那先学什么」），从最近轮次抽取主题拼接成完整问句；抽不到就返回 None。
- 返回 None 不会硬猜，而是进入澄清：让用户补题号或选项。19 轮里指代消解率 1.0，但样本只有 19 轮。
- 天花板很清楚：复杂指代（「它为什么错」「上面那个」）会漏；多主题会话可能指错。
- 升级顺序：先补模式和负样本测试，再考虑小模型分类器；不要一上来上 LLM，成本和延迟都不划算。

**别踩**：不要用 19 轮的 1.0 证明「规则足够」。

**要补**：指代覆盖率、误消解率，需要构造 100+ 轮多话题集。

### Q10. 成本多少？

**结论：多轮评测 19 轮总成本 0.1744 元，约 0.92 分/轮；但这是估算下界，不是账单。**

- 实现：每次 LLM 调用记 prompt/completion tokens，按 `PRICE_PER_1K` 人民币单价表折算，保留 6 位小数，写进 trace 和前端每轮元信息。
- 口径问题：当前 `.env` 用的模型不在单价表里，走默认价（0.002 元/1K prompt + 0.008 元/1K completion），所以是估算。
- 还有一处漏计：表达式抽取的 LLM 调用 token 没有汇入 state，严格说成本会略低。
- 延迟参考：Agent 21 题平均 5.6 秒；60 题端到端 P50 15.8 秒。两者场景不同，不要混。

**别踩**：不要说「一轮不到一分钱所以很便宜」，先说是估算。

**要补**：供应商真实账单、按题型的分项成本、P95 成本【待补】。

### Q11. 延迟多少？

**结论：检索 P50 约 50ms 级；Agent 21 题平均 5.6 秒；60 题端到端 P50 15.8 秒；P95 和并发延迟没测。**

- 检索：dev P50 报告约 50ms，holdout 54ms；README 旧口径写 35–49ms，和报告不一致，以报告为准。
- Agent：dev 21 题平均 5.6 秒（纯 LLM 3.0 秒、单轮 RAG 5.1 秒），说明工具轮次是主要增量。
- 60 题端到端 P50 15.8 秒，明显高于 21 题，主要差在生成长度和空回答重试。
- 没测：P95/P99、并发下的排队时间、冷启动。

**别踩**：不要把 P50 说成「平均响应时间」，也不要把不同集的延迟拼在一起。

**要补**：P95/P99、并发压测、首 token 延迟【待补】。

### Q12. 并发怎么办？

**结论：当前是单机串行，明确不支持高并发；这是已知短板，不是隐藏问题。**

- `AgentRunner` 用 `Lock` 串行化；`ToolGuard` 是进程级窗口（单轮 6 次、每分钟 60 次），不能按会话隔离。
- 多用户同时提问会排队；多副本部署时限流和记忆都不一致。
- 升级路径：工具实例 per-run 或池化、会话外置 Redis、限流按 session/tenant 维度拆、再加压测。
- 现阶段定位是单机演示与个人备考，不是生产多租户。

**别踩**：不要说「Streamlit 天然支持并发」，它也不是为多租户设计的。

**要补**：QPS、P95、错误率、内存占用【待补】。

### Q13. 知识库没有的问题怎么处理？

**结论：先检索，没证据就明确说没有，落 `no_evidence`，不拿模型记忆硬答。**

- 流程上，`observe` 发现没有 contexts、也没有成功工具时，不进入生成，直接落 `no_evidence`；生成返回空正文也归到 `no_evidence`。
- 如果是「考点定位不到」，不是硬答，而是走澄清，返回 top 5 高频标签让用户选。
- 边界：如果问题超出 408 但模型愿意答，仍可能答；当前没有做域外分类器。
- 体验上，前端能区分「没查到」和「工具失败」，不会都显示成一句抱歉。

**别踩**：不要说「模型会自己判断不知道」，判断是流程做的。

**要补**：域外问题的拒答率/误拒率【待补】。

### Q14. 上线后怎么监控？

**结论：现在有调用级 trace 和评测报告，没有线上监控体系；先讲能观测什么，再讲缺什么。**

- 可观测：每轮写 stop_reason、轮次、工具调用与失败、token、成本、trace id；`/v1/trace/{request_id}` 可查；前端可展开推理链。
- 可评测：19 轮多轮报告、60 题端到端、对抗评测都是离线脚本产出 JSON/Markdown。
- 缺的：没有接 Prometheus/OTel，没有告警、没有线上采样、没有用户反馈闭环；`no_evidence` 率和空回答率目前靠离线统计。
- 如果上线，第一优先监控四个指标：空回答率、no_evidence 率、工具失败率、单轮成本与 P95。

**别踩**：不要把「有日志」说成「有监控」。

**要补**：监控面板、告警阈值、线上采样与回归【待补】。

### Q15. 如果重做会改什么？

**结论：先补评测，再谈架构；架构上最想改的是会话外置和工具并发。**

- 第一，先做 holdout 三路 baseline 和 bootstrap CI，否则所有「Agent 更好」都站不住。
- 第二，把引用编号校验纳入 `verify` 的硬拦截，低分重写一次，而不是只记录。
- 第三，会话记忆外置 Redis，工具实例池化，补并发压测。
- 第四，指代消解从 4 类规则扩到可评测的分类器，但必须先有覆盖率/误判率指标。
- 不会改的：有界循环、7 终态、工具契约。这些是项目最稳的部分。

**别踩**：不要为了显得有反思而否定核心设计。

**要补**：每项改造的预期收益都需要实验，不能口头承诺。

### Q16. Agent 95.2% 比单轮 RAG 85.7% 高，能说明什么？

**结论：只能说明在这 21 题上方向一致，不能说明显著更优。**

- 21 题配对集：纯 LLM 90.5%、单轮 RAG 85.7%、Agent 95.2%；Agent 比单轮高 9.5 个点。
- 但样本只有 21 题，bootstrap 置信区间下界到 0；计算题子集里 Agent 是 83.3%，纯 LLM 是 100%，Agent 反而输。
- 合理解释：概念题上工具和校验有帮助；计算题上表达式抽取可能引入新错误。
- 所以对外只说「dev 上方向一致，计算题是弱项」，并把 holdout 三路对照列为待补。

**别踩**：不要拿 95.2% 当项目主卖点，主卖点是链路和可评测性。

**要补**：更大样本、分题型误差分析、holdout 三路对照【待补】。

### Q17. 7 种 stop_reason 有什么用？分布呢？

**结论：它是 Agent 的可观测契约，保证任何结束都有原因；但真实分布只覆盖了 2 种。**

- 7 种：`answered`、`clarification`、`no_evidence`、`tool_error`、`budget`、`max_rounds`、`verify_retry`。
- 作用：前端能区分「正常答」「反问」「没证据」「工具坏」「超预算」「超轮次」「校验重写」，排障不用猜。
- 现有分布：19 轮里 `answered` 15、`clarification` 4；其余 5 种只有单测覆盖，没有评测分布。
- 这也是一个诚实的短板：故障注入评测还没做。

**别踩**：不要编造 budget / max_rounds 的线上比例。

**要补**：故障注入评测（超时、空检索、LLM 不可用、强制超轮次）【待补】。

### Q18. 选择题为什么要短路澄清？不会误澄清吗？

**结论：只对「有指代但缺上下文」的选择题短路，目的是不浪费检索和 LLM；误澄清率没测。**

- 触发条件很窄：问句含「这题/这道题/选什么/下图/如图」之一，且没有题号，且四个选项都为空。
- 命中后直接返回两个选项：给真题编号，或直接发 A/B/C/D 文字；不检索、不调 LLM，成本为 0。
- 另一类澄清是「考点类问题但定位不到考点」，返回 top 5 高频标签。
- 边界：澄清召回率 1.0（4 个用例全中），但精确率/误澄清率没有单独指标；问句模糊时可能多问一次。

**别踩**：不要说「所有选择题都会澄清」，实现只覆盖两类。

**要补**：误澄清率、澄清后解决率、平均多一轮的体验成本【待补】。

### Q19. 用户画像怎么用？会不会过度拟合？

**结论：画像是事件聚合的派生视图，只做规划加权，不直接改检索结果。**

- 单一事实来源：用户问题事件、规划事件、作答事件；画像按标签聚合，不单独存一份「用户标签」。
- 用法：对抗规划按画像给薄弱科目和错题考点更高优先级；前端会预填薄弱科目。
- 答错考点权重最高，这是有意设计：错题比「问过」更能说明薄弱。
- 边界：样本少时画像会偏；匿名 `cid` 存在 URL 里，换设备就断；没有做冷启动策略。

**别踩**：不要说「个性化推荐」，目前只到规划加权和真题推荐。

**要补**：画像对规划质量的增益评测、冷启动与偏差分析【待补】。

### Q20. 重排为什么关掉？

**结论：交叉编码器重排在消融里是负收益，所以没上线；这是项目里最值得讲的负结果。**

- 消融对比了开/关重排的检索指标，重排没有带来稳定提升，反而增加延迟和依赖。
- 项目选择保留「三路融合 + 小节去重」这条更轻的链路，把复杂度留给有收益的地方。
- 这也是评测驱动的体现：不是「论文里有 rerank 就上」，而是看自己的数据。
- 边界：负收益可能和语料规模、chunk 粒度、模型选择有关，不能外推成「重排无用」。

**别踩**：不要说「重排没用」，说「在这套数据和粒度下没有正收益」。

**要补**：不同 chunk 粒度、不同 rerank 模型下的复测【待补】。

## 4. 短板与加分话术

> 原则：先承认，再给证据，最后给升级路径。不要辩解，也不要把短板说成「设计选择」就结束。

### 4.1 缺 baseline 对比

**被问到时怎么答（逐字）**

> 有，但不够。检索侧有 dense/sparse/BM25 和融合的消融；Agent 侧有 dev 21 题的三路对照：纯 LLM 90.5%、单轮 RAG 85.7%、Agent 95.2%。缺的是 holdout 99 题上的端到端三路对照，所以我不说「Agent 在未见年份上显著更好」。这块我列成了第一优先补数项：同 prompt、同集、bootstrap CI，再加成本和 P50/P95。

**如何转化为加分**

- 主动区分「有 baseline」和「baseline 够不够」，体现你知道什么叫可证伪。
- 顺带讲 21 题计算题 Agent 输给纯 LLM（83.3% vs 100%），说明你不是只看赢的那部分。
- 加分句：「我更愿意先承认样本小，再把补数计划说清楚，而不是拿 21 题下结论。」

### 4.2 规则指代消解的天花板

**被问到时怎么答（逐字）**

> 规则只覆盖 4 类高频模式，复杂指代会漏。我的策略是「解不出来就不猜」，返回 None 走澄清，宁可多问一句，也不拼错主题。19 轮里消解率是 1.0，但样本太小，我不会拿它证明覆盖面。下一步先补「它为什么错」「上面那个」这类模式，再考虑小模型分类器，前提是先有覆盖率和误消解率指标。

**如何转化为加分**

- 把「保守」讲成产品判断：备考场景答错比多问一句代价高。
- 说明升级顺序：规则 → 模式扩充 → 分类器，而不是直接上 LLM。
- 加分句：「规则的上限我知道，但它的失败是可预测的，这比不可解释的误消解更适合当前阶段。」

### 4.3 内存记忆重启即失

**被问到时怎么答（逐字）**

> 是，当前记忆是进程内的 LRU，200 个会话、2 小时 TTL，重启或换实例就丢。我是刻意先不做持久化：避免引入会话库、隐私保留策略和多副本一致性成本。升级路径很明确，Redis 按 session TTL + LRU，或者接 LangGraph checkpointer；但上线前要先定义保留期限和脱敏。

**如何转化为加分**

- 主动说出代价（重启丢、 多副本不一致），比面试官追问出来更好。
- 讲清楚「不是不会做，是当前阶段不需要」，并给出触发条件：多实例、需要跨设备、需要审计。
- 加分句：「记忆的价值要用评测证明，我还没做压缩对回答质量的影响评测，所以不急着上持久化。」

### 4.4 单机无并发与延迟数据

**被问到时怎么答（逐字）**

> 当前是单机串行，`AgentRunner` 用 Lock，`ToolGuard` 是进程级限流，多用户会排队；P95、QPS、并发错误率都没测。已有的延迟是检索 P50 约 50ms 级、Agent 21 题平均 5.6 秒、60 题端到端 P50 15.8 秒。要上线我会先做三件事：会话外置、工具实例池化、压测出 P95 和排队时间。

**如何转化为加分**

- 不把「单机」包装成「轻量」，直接说定位是个人备考/演示。
- 给出明确的并发改造顺序，显示你知道瓶颈在哪（锁、进程级限流、内存记忆）。
- 加分句：「没有并发数据之前，我不会承诺 SLA，这是我对线上指标的基本敬畏。」

### 4.5 Week 4 收尾项（60 题全量评测、3 个 demo、文档、CI）

**被问到时怎么答（逐字）**

> 收尾项四项进度不一样。60 题端到端已经跑过：78.3%，排除 8 个空回答后可判题 90.4%，P50 15.8 秒；但它记录在优化日志里，不是独立报告，也没有三路 baseline。3 个可重复 demo 还没做成独立资产，目前靠 Streamlit 现场操作。文档基本齐：README、优化日志、面试材料。CI 只跑 10 个 adversarial 单测，不是全量 223 个，这是我知道的缺口。

**如何转化为加分**

- 用「已完成 / 部分完成 / 未完成」三分法回答，避免一句「都做完了」被追问穿。
- 主动说 60 题空回答 13.3%，并解释这是 flash 模型输出上限和上下文预算导致，不是准确率作弊。
- 加分句：「我把收尾项也当成评测的一部分：demo 要可重复，CI 要能防回归，不然文档写得再漂亮也不算交付。」

## 5. 现场演示脚本

> 演示目标不是「功能全」，而是三个能力各留一个记忆点：**多轮指代、澄清短路、成本与终态可见**。
> 演示前 5 分钟检查：`docker compose up -d`（Qdrant + Neo4j）、`.env` 有 LLM key、`streamlit run app/streamlit_app.py` 已起、浏览器打开 :8501。
> 页面 tab 顺序：💬 问答 → 🤖 Agent 备考助手 → 📊 考点分析 → 🔍 检索调试 → 🛡 对抗规划 → 📈 实验数据。

### Demo 1：多轮追问与指代消解

**要证明**：同一会话内，第二问的「那 2021 年呢」被还原成完整问句，而不是重新检索一个孤立问题。

**操作步骤**

1. 打开「🤖 Agent 备考助手」。
2. 第一问输入：`死锁这个考点历年考过几次？`
3. 等回答出现，展开「推理链与工具调用」，让面试官看到走的是 exam 路由、调用了真题统计。
4. 第二问输入：`那 2021 年呢？`
5. 看本轮回答上方的灰色小字「已按上轮语境改写为：…」，确认它变成类似「死锁在 2021 年考过几次？分别是哪些真题？」，而不是空的。
6. 第三问输入：`那先学什么？`，展示它沿用「死锁」主题并给出学习顺序。

**预期现象**

- 第二问的 resolved query 里出现「死锁 + 2021」，不是空的。
- 第二问轮次比第一问多（多轮评测里同类用例是 2 轮），说明补了工具调用。
- 每轮下方有 stop_reason 和成本；历史记录保留在同一会话。

**失败兜底**

- 若 resolved query 为空：不要硬圆，直接说「这条规则没覆盖，按设计会走澄清或按原句检索」；然后改用「死锁在 2021 年考过几次」显式问句继续演示。
- 若检索为空或工具失败：展示 stop_reason（`no_evidence` 或 `tool_error`），说明这正是终态契约的价值，再换「进程和线程的区别」这类稳定概念题。
- 若服务没起：改用 `docs/interview-prep.md` 的多轮评测表 + `data/eval/multi_turn_report.json` 讲同一件事，明确说「现场环境没起，数字来自离线报告」。

### Demo 2：选择题澄清（不检索、不调 LLM）

**要证明**：信息不足时 Agent 会停下来反问，而且这个短路是省成本的，不是「答不动」。

**操作步骤**

1. 仍在「🤖 Agent 备考助手」，新开一个会话或清空上下文。
2. 输入：`这道题选什么？`（不要带题号，也不要贴选项）。
3. 观察返回：出现两个结构化选项——「告诉我真题编号（如 2009-04）」和「直接把 A/B/C/D 四个选项的文字发给我」。
4. 点第一个选项，或手动输入 `2009-04`，观察进入下一轮解析。
5. 看本轮元信息：stop_reason 是 `clarification`，工具 0 次、0 轮；成本为 0 时不显示金额，这本身就是「没调 LLM」的证据。

**预期现象**

- 澄清是终态：不触发检索，不调用 LLM，返回很快。
- 前端把选项渲染成按钮，点击后作为下一轮问题发回。
- 元信息里能看到 `clarification`，与正常回答的 `answered` 明确区分。

**失败兜底**

- 若没有出现澄清而直接作答：说明当前问句没命中触发条件（可能带了隐式上下文），改用更标准的「这道题选什么？」重试；仍不触发就承认「触发条件很窄，这是为了避免误澄清」。
- 若按钮点击无反应：直接手动输入选项文本，说明「按钮只是把文本发回，链路是同一条」。
- 若题号解析失败：换一个确定存在的题号，或改演示「考点定位不到 → 返回 top 5 高频标签」这一类澄清。

### Demo 3：成本与 stop_reason 可见

**要证明**：每次调用都能看到 token、人民币成本、终态和工具轨迹，不是一个黑盒回答。

**操作步骤**

1. 在「🤖 Agent 备考助手」提一个需要工具的问题，例如：`死锁这个考点历年考过几次？`
2. 展开回答下方的「推理链与工具调用」，逐项指出：路由、工具名、耗时、成功/失败。
3. 指出每轮元信息里的 `stop_reason · 成本`，说明 `answered` 与 `no_evidence` 的差别。
4. 切到「📈 实验数据」，展示 19 轮多轮评测的汇总：通过率 94.7%、澄清召回 1.0、指代消解 1.0、工具失败率 3.0%、总成本 0.1744 元。
5. 补充口径：「成本按默认单价估算，当前模型不在单价表里，所以这是下界，不是账单。」

**预期现象**

- 单轮回答下方能同时看到终态与成本。
- 实验数据页能看到 stop_reason 分布：answered 15、clarification 4；其余 5 种没有评测分布，主动说明只有单测。
- 面试官能看懂「为什么结束」，而不是只看答案对不对。

**失败兜底**

- 若 LLM 不可用：成本与生成都不可用，改演示「🛡 对抗规划」的离线规则模式（关闭 LLM 文案），它约 0.5 秒出完整 Plan，再口述成本模块的设计。
- 若前端成本字段为空：直接打开 `data/eval/multi_turn_report.json`，讲 `total_cost_cny`、`stop_reason_dist`、`rows[].cost_cny` 三个字段。
- 若被追问「成本为什么这么低」：承认模型不在单价表、表达式抽取 token 漏计，说明这是估算下界，不辩解。
