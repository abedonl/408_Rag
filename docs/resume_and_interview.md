# 简历描述与面试话术

> 基于当前实测数字。面试时优先讲**判断过程和负结果**，而不是罗列技术栈。

---

## 一、简历条目

**408 考研 RAG 备考助手（个人项目）**

- 构建面向 408 考研的检索问答与考点分析系统：720 道历年真题（2009–2026）、
  5296 个教材 chunk、6182 个知识点图谱；按题型自适应选择召回路
  （dense + BGE-M3 sparse + BM25，去掉图谱）+ 加权 zscore 融合 + 小节去重，
  题级命中 **Accuracy@10 0.668**、MRR 0.371、检索 P50 35–49ms。
- **held-out（2023–2026，60 题）端到端选择题准确率 78.3%（排除空回答 90.4%）**，
  防泄漏校验通过；实现主模型空正文自动降级到备用模型，单测覆盖。
- 设计可复现的检索评测链路：ground truth 由 `题目 tags → 知识点 → 教材小节` 构造，
  补充 Precision@k 与题级 Accuracy@k；通过过滤章节导语小节、修复 tag 映射泛化节点，
  把可用评测题从 365 提升到 452。
- 用消融实验否定三个常见优化：交叉编码器重排（−5~7pp）、原生 BM25 混合
  （并集 +2.7pp 但融合 −1pp）、图谱查询扩展（与节去重收益重叠）；
  并在 Oracle 候选集（85% 含正确答案）上验证重排器天花板。
- LangGraph Agent 编排 9 个工具（三路检索 / 计算器 / SVG 图形解析 / 考点统计 /
  前置学习路径），考点分析结论**可溯源率 100%、押题表述 0**。

## 二、面试问答

### Q1：你的召回率怎么只有 0.35？

先区分口径：

- **Recall@10 = 0.382**：命中的 GT 小节 chunk 数 / 该题全部相关 chunk 数。
- **Accuracy@10（题级命中）= 0.668**：top-10 中只要命中该小节任意 chunk 就算 1。
- 同配置下去掉「小节去重」：Recall@10 约 0.51、Accuracy@10 约 0.60。

为什么有取舍：GT 是**一个教材小节**，该小节常被切成 2–5 个 chunk。
不去重时 top-10 被同一小节的多块占满，题级覆盖反而低；去重后每节只留 1 条，
覆盖更多不同小节，题级命中从 0.597 升到 0.633，但 chunk 级 Recall 必然下降。

**产品口径选 Accuracy@10**：用户要的是「有没有拿到正确的那一节」，不是「拿到该节多少块」。

补充上限数据：三路并集 Recall@10 0.668、@50 0.889；放大候选池对 @10 没有帮助，
瓶颈在融合排序而不是召回深度。

### Q2：为什么用了 reranker 反而下降？

不是接入错误。做了两层验证：

1. **整链路消融**：加 bge-reranker-v2-m3 后 Recall@10 下降 5–7pp。
2. **Oracle Rerank**：固定四路 top-50 候选（85% 的题候选集里包含 GT），
   只让 reranker 排序：Hit@10 只 +1pp，MRR +0.0013，nDCG 略降。

结论：不是候选不够，是这个交叉编码器的偏好与本任务的相关性定义不一致——
它偏向「看起来在回答这道题」的文本，而正确答案是**概念讲解章节**。

### Q3：Agent 比单轮更好吗？RAG 到底有没有用？

**2026-10-29 重跑（dev 21 题配对，PROD 配置 + 空回答修复）**：

| 路径 | 准确率 | 95% CI | 空回答率 | P50 |
|---|---|---|---|---|
| 纯 LLM（无检索） | 90.5% | [76.2, 100] | 0% | 3.0s |
| 单轮 RAG | 85.7% | [66.7, 100] | 0% | 5.1s |
| Agent | **95.2%** | [85.7, 100] | 0% | 5.6s |

- Agent − 单轮 +9.5pp，CI [0, +23.8]；**下界是 0，不能说显著更好**。
- 单轮 − LLM-only −4.8pp，CI [−23.8, +9.5]；**dev 上没有可证明的 RAG 准确率增益**。
- 空回答从旧版的 5/7 改错原因降到 **0%**：prompt 第一行先写答案、max_tokens 3000、
  空正文缩短上下文重试。
- LLM-only 90.5% 说明 2009–2022 公开真题很可能在预训练语料里；RAG 的价值要讲
  **出处/引用、held-out/私有题、不可参数化的信息**，不要拿 dev 准确率证明 RAG。

> 旧 25 题（单轮 80% vs Agent 64%）是旧检索配置 + 空正文未修的结果，
> 只作为过程记录，不再作为当前结论。

25 题分层抽样：单轮 80% vs Agent 64%。逐题归因后：

- 7 个 Agent 改错的题里，**5 个是空正文、2 个是输出没按 `答案：X` 收尾**，
  没有一题是工具结论错误。
- 当前 endpoint 的 flash 模型会强制思考，Agent 的 prompt 更长（图解析/统计），
  reasoning 更容易吃光 `max_tokens`；单轮 prompt 短，反而更稳。

但工具链在能力边界上是有效的：2009-04（四棵 AVL 树）靠 SVG 拓扑重建答 B，
2014-24 靠本地计算器答 B。这两个是单轮按定义做不到的。

**诚实结论**：在这批样本和这个模型上，Agent 的收益被模型输出稳定性抵消了；
要公平比较 Agent 设计，需要换到能稳定关闭思考的模型重跑。

补充：已做模型 A/B（同 20 题）——sensenova 80%（可判 88.9%）/ 空 2、
glm-5.2 75% / 空 0、deepseek-v4-flash 75%（可判 83.3%）/ 空 2 但 RPM 低延迟 24s、
deepseek-flash 70% / 空 1。二选一都有损失，最终实现**主模型空正文时自动降级
到备用模型（glm-5.2）**，并用单测覆盖降级路径。

**补充：LLM-only 基线（2026-10-29，dev 46 题）**：不检索、只靠模型参数化知识，
准确率 **87.0%**（40/46），空回答 0。这说明 2009–2022 真题很可能已经在预训练语料里，
**dev 上的准确率不能证明 RAG 的价值**。要回答「RAG 有没有用」，必须用模型没见过的
私有题/最新题；当前项目能证明的是检索指标、引用可溯源和工具边界，而不是
「RAG 比裸模型更准」。这条结论要主动讲，不能等面试官问。

**Agent 的成本按题型分解**（比「9 个工具」更能说明设计意图）：

| 题型 | 路由 | Agent 准确率 | 单轮 | Agent P50 | 延迟倍数 |
|---|---|---|---|---|---|
| 概念 | 直连检索 | 88% | 88% | 6.3s | **1.0×** |
| 计算 | 检索+计算器 | 75% | 100% | 33.2s | 2.2× |
| 图表 | 检索+图解析 | 25% | 62% | 59.6s | **3.6×** |

概念题不额外开销、计算/图表才走工具——这是有意的分流。
当前短板是图表题的空正文（prompt 更长，思考吃光预算），不是工具数量。

### Q4：怎么保证评测没有数据泄漏？

- held-out（2023–2026）的**官方解析从未入库**：`chunk_explanations` 直接跳过这些年份；
  入库前还有 `assert_no_holdout_leak` 兜底。
- 检索层用 `exclude_years` 二次拦截。
- 评测启动时跑 `check_no_leak()`：扫描索引，确认 explanation chunk 的年份不含 holdout。
  不通过直接中止。
- 评测检索时排除 `source=explanation` 与 `chunk_class=exercise`：
  解析和「答案与解析」小节逐字含题干，不排除就是自匹配作弊。

### Q5：ground truth 怎么构造？质量怎么保证？

链路：`题目 tags → tag_kp_mapping → 知识点 → 教材小节 → 该节全部 chunk`。

踩过的坑和改进：

- 章节导语（复习提示/考纲内容/小结）会把整章术语列一遍，导致 GT 指错；
  已排除，GT 指向导语的题从 7 降到 0。
- tag 映射曾指向「栈」「方式」「性能」这类泛化节点；改为过滤单字节点、
  按字面覆盖度排序，并在 GT 端过滤泛化标题。168 题 GT 变化，指标几乎不变
  —— 说明污染影响个例判断，不影响均值。
- 映射质量是评测链上游：未匹配的 tag 对应的题**不计入分母**，如实报告，
  不给假 GT。当前 720 题中 551 题可用。

### Q6：为什么不微调 embedding？

评估后决定不做：

- dev 只有 452 个「题干 → GT 小节」正例，对比学习容易过拟合；
- 当前 sparse（0.58@10）已强于 dense（0.55@10），瓶颈在融合与 GT，不在 embedding；
- held-out 只有 99 题有 GT，微调后验证噪声大，容易得出假结论。

如果要做，最小方案是：难负例（同科 BM25 top-10 非正例）+ 只训最后两层，
同时在 dev 和 held-out 上分别报告，防止过拟合。

### Q7：项目里最难/最有价值的判断是什么？

**先修评测，再调检索。** 最初的 Recall 0.495 让人以为检索差，
但抽检发现一部分是 GT 指到了章节导语、tag 映射到了泛化节点。
修完后指标没怎么涨——这个「没涨」本身是关键信息：它证明剩余问题在排序和生成侧，
而不是评测噪声。

后续的负结果（reranker、BM25、图谱扩展）也都是先做对照实验再做决定，
没有因为「论文里说有效」就直接上线。

### Q8：和同类开源项目怎么比？

不直接比总分。竞品报的是自建 394 道混合题上的选择题准确率 91.62%，
题源与口径都不同；本项目是 720 道纯真题 + 严格年份 hold-out + 组件消融。
差异化的点是**能说清数字由哪些组件贡献**，以及**负结果可复现**。

## 三、诚实局限（面试可主动说）

1. 检索指标在「单小节 GT」口径下不高；放大候选池不能解决排序瓶颈。
2. Agent 在选择题上没有赢，原因是模型输出稳定性，需要换模型重跑。
3. 图表题 T3（位图、28 题）没有可用的 VLM，评测里如实标注未覆盖。
4. 前置依赖边只覆盖同父相邻兄弟（148 条），跨章依赖没有，尚未人工抽检。
5. 生成侧 Oracle 可判题 75%，计算题可判题 87%；空回答率 23% 是当前最大噪声源。
